# Passwords: one page over any password manager

Clickdummy, 2026-11-17. Open [index.html](index.html) directly; it needs no server. It has two parts: the Passwords page (`#/passwords`) and Settings › Sources (`#/settings/sources`, the gear at the top right).

## The question

Could knobas show a team's passwords next to the work without becoming a password manager? The page has to work the same whether the passwords live in a KeePass file, a Pleasant Password Server or Bitwarden/Vaultwarden.

## What the mockup assumes

- **A password manager is a source.** It is added, signed in, synced and removed in Settings › Sources, next to Jira and Gitea, through the same *Add a source* dialog. KeePass file, Pleasant Password Server and Bitwarden or Vaultwarden are three adapters in its list. Anything else, such as 1Password, HashiCorp Vault or pass, would come in as an external adapter.
- **Passwords is a role** (ADR-0029). The shell draws the role and never a source. Every adapter implements one interface:
  - The minimum is to list entries (title, username, address, folder path, when changed) and to read one secret when asked.
  - Everything else is optional, and each adapter declares what it supports: writes (add, edit, move, change the password), one-time codes, attachments, history, expiry dates, usage comments, an audit log, access requests.
  - The page draws a control only where the entry's source declares it. The source's page in Settings lists what that source declares.
- **The Passwords page names a source in one place only: the top of the tree.** There are no vendor marks and no *Open in Pleasant*. With one password source, its folders are the tree. With more than one, each source's folders sit under one top folder named after the source (*Team passwords*, *Tidewater org*), so a path that begins with it says which collection an entry belongs to without naming a product. Without that, Pleasant's `Tidewater/Payments` and a Bitwarden collection `Payments` show up as two unexplained `Payments` folders, which the *Pleasant and Bitwarden* scenario shows. That top folder is part of the path in the breadcrumb and on rows in mixed lists. A source whose folders all sit under one root folder, as Pleasant's sit under `Tidewater`, skips that root: *Team passwords / Payments / Prod*, not *Team passwords / Tidewater / Payments / Prod*. Writes put it back. A new entry asks only for a folder, and the folder decides which source the write goes to.
- **The master password is the source's credential.** A KeePass file's master password, and Bitwarden's API key plus master password, are kept in the macOS keychain like any source's token. The adapter opens the file or vault with them at every sync and every read. Nothing ever locks, and nobody retypes anything. The source's page has *Change* for when the master password changes.
- **Entries sync into the mirror; passwords never do** (decided 2026-11-17). Title, username, address, folder path and notes sync like any other source's items, so search always finds them. A password, a one-time code or an attachment is a live read through the adapter each time someone shows or copies it, the same as ADR-0032's live reads. When a source stops answering, its entries stay listed with the time of the last sync, and no password can be read from them.
  - One exception, and it is not the mirror: **a one-time code is made on this machine.** The seed behind it, the TOTP key, is read once when an entry with a code first syncs, and again when the entry changes. It is kept in the macOS keychain next to the source's credential, never in Postgres. So codes work while the source is down or slow, and copying one reads nothing from the source. The cost is one read per entry that has a code, once, not every password. Where a source logs reads, that is one audit line per such entry. It also means anyone who can open this Mac's keychain has the second factor. That is no worse than keeping the code in the same password manager as the password, which is what these entries already do. The *A source offline* scenario shows it: the Bitwarden org is down, its password can't be read, its code still runs.
    - On Pleasant the codes come from the team's TOTP plugin, which keeps each seed in custom fields on the entry. Pleasant's REST API (v5) returns an entry's `CustomUserFields` and `CustomApplicationFields` with the entry itself; only the password has its own request (`/api/v5/rest/entries/{id}/password`, a POST with the comment where one is required). So the seed arrives with the sync that lists the entry, and no separate read is needed. That changes two things:
      - The Pleasant adapter has to know the plugin's field names and take those fields out of the item before it reaches the mirror, moving the seed to the keychain. A generic adapter would copy every custom field into `sync.item.payload`, seed included, and the entry page would draw it as a copyable field.
      - Anyone who can view the entry in Pleasant can read the seed without the password request, so without the audit line and without a usage comment. That is how the plugin already works, not something knobas adds.
      - Which plugin the team uses is not known. The adapter does not need to be told: it reads every known format and says on the source's Settings page which one it found. The formats: `TimeOtp-Secret-Base32` (built into KeePass 2.47+), `TOTP Seed` and `TOTP Settings` (KeeTrayTOTP), `otp` as `key=…&step=30&size=6` (KeeOtp), `otp` as an `otpauth://` URI (KeePassXC). To check by hand: open an entry with a code in Pleasant's web client and read its custom field names, or look under Tools › Plugins in the KeePass client.
      - Copying a code asks for no usage comment, even where the folder requires one, and writes nothing to Pleasant's audit log (decided 2026-11-22). Pleasant never sees the code being used, so a comment would go nowhere. Only an access request still applies.
  - Rejected: storing encrypted copies of passwords in the mirror (a `sync.secret` table sealed with a key kept in the source's keychain entry). It would have made a slow Pleasant fast. But filling that store in the background means reading every password, which writes an audit-log line under your name for each one.
- **Folders are a tree, and an entry never loses its place in it.** Pleasant folders and KeePass groups nest, and Bitwarden nests folders and collections by naming them `Parent/Child`. So the role's minimum includes each entry's folder path, sent as a list of segments, because a folder name can contain `/`.
  - The tree unfolds down to the open entry, and a folded folder that holds it is drawn bold.
  - A folder shows its own entries and everything under it, grouped by subfolder.
  - Wherever a list mixes folders, each row carries its path, and search matches the path too. The breadcrumb is the full path.
  - Folder rules inherit down the tree.
  - Edit moves an entry only within its own source.
- **Copying asks nothing by default**, as Pleasant's own client does. A source with an audit log records the read on its side, and the entry's history shows it. A prompt appears only where an admin has required [usage comments](https://keepasshub.com/info/keepass-hub/e-access-levels/usage-comments) for a folder or entry: see the *Usage comments on* scenario. Pleasant wants a comment for each use, so knobas asks every time. It fills in your last comment, or else your current ticket, and Enter sends it.
- **Passwords are only passwords, in knobas as it is today.** An entry is not linked to assets or to knobas' own sources, and nothing else in knobas reads a password: no shell, no sign-in. An address opens in the browser when it is a web address and is copied otherwise. The top bar and Settings are the app's own: the page is one more section next to Docs.
- **Needs attention** collects entries that expire within 14 days, and entries unchanged for more than 180 days.
- **A copied secret burns a 20-second fuse** in the status bar. A revealed password is drawn as numbered cells coloured by character class.

## Open questions

1. Moving an entry between sources would be a copy and a delete across two adapters. Allow it, or keep moves within one source as the mockup does?
2. Does knobas ever show a password, or only copy it? The mockup allows both.
3. Entry titles synced into the mirror are copied into `knobas.entity.title`. That table goes into every backup and every *share with a colleague* export (`CONTEXT.md`, Share export). Should password entries be kept out of the entity table or out of share exports, or is a title acceptable there?
4. Usage comments: which Pleasant actions trigger them (view, copy, the one-time code, an attachment) needs checking against a real server with comments turned on. The mockup asks on show, copy and save.
5. Access requests: should approvals arrive in knobas' Inbox, or stay with the password manager?
6. Does reading entries at sync write audit lines? The seed only stays out of the audit log if the read that lists entries and their custom fields is not logged as a view. If Pleasant logs one line per entry per sync, a sync every few minutes would fill the log faster than reading passwords ever would. Check against a real server before the adapter syncs custom fields; if it is logged, sync the fields only when an entry's change date moves. Or sync that source by hand only: then audit lines appear only when you press *Sync now*, and codes keep working between syncs because their keys are in the keychain. The mockup's Team passwords source is set that way. knobas has no by-hand setting today: a source syncs every 20 s to 1 hour, or is turned off, and a turned-off source does not sync at all. So *Only when I press Sync now* would be a new interval choice for every source.
