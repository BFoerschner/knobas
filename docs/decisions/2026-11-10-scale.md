# 2026-11-10: knobas at Björn's mirror's size

**Asked (Björn, on PR #2479):** "I have like 5k confluence pages, 20k tickets, 4k TeamCity objects and 10k gitea items, and the ui feels really slow. I think it's not the search itself, but the rendering just can't keep up anymore. Please review, see where the performance drop is and fix it."

**Measured** with `?fake-ipc&fake-scale` (`app/src/lib/shell/dev/fake-scale.ts`: that corpus, deterministic) in headless Chrome, every place a person waits or types, and against the responsiveness probe's 23,660-item database for the reads behind them.

**A page you leave stops reading.** Each address hands the kept pages a new shell context, and the role frame rebuilt the object holding a page's `syncRevision` from it, so a page the reader had just left read again as if a sync had ended: leaving Code read its 4,400 pull requests and every repository (1.2 MB in 11 reads) and asked 132 checkouts for their state, each a `git status` in the app; leaving Docs read its 5,000-page tree (566 KB). Code reads on its return, as before; Docs reads when a run of its sources ends, as it says it does.

**The board's *Show more* adds fifty.** One press used to draw a column whole, and to read every column at that column's count: at 20,000 tickets, *Show 8016 more done* read 5.8 MB (1.1 s on the probe's database), drew 73,311 nodes and took the heap from 43 to 282 MB. A press now adds fifty cards and reads only those (*Show 50 of 8013 more done*), and past 200 drawn the column offers *See all 8019 in the list*, which opens the list on its statuses, because the list draws only the rows on screen. The design system's *Layout* says so.

**A pipeline's history draws the days near the screen.** Scrolling back through a history held every run read: 60 wheel steps reached 35,315 nodes, 21 long tasks and 133 ms frames. Past thirty days the page draws a day at a time around the screen (`Windowed`, as the other long lists do); it looks the same.

**A space's page draws the pages near the screen.** *Engineering handbook* at 2,250 pages drew every row, 4,575 nodes; windowed, 145, and it looks the same.

**Monitors windows from 100 rows.** A monitor's row is 71 nodes with its bars, and every list windowed from 300, so the live scale estate's 218 monitors drew 15,316 nodes and a 140 ms frame in the app's window; now 1,738 and none.

**A typed word reads the stored assignee.** On the live scale estate (20,016 Jira tickets) a word in the Tickets box took 445 ms in the search before the board read began, 400 of them walking every ticket's payload for its declared assignee. The search now reads `sync.item_field`'s stored assignee where it holds one for these declarations, as the board already did (#2184), and walks where it does not, the same answer: *pay* 440 to 92 ms, *mara* 617 to 113 ms, a word nothing holds 614 to 117 ms.

**Typed words wait for the board read still out.** A typed read takes 160 to 240 ms on the probe's database, so a key every 150 ms had two or three running against each other. Now one is out at a time: the next reads the words as they are when it answers, or after 400 ms if it hangs.

**The list showing every ticket reads the capped board while you type.** After the list's *Show N more*, each key read every match: 5.5, 3.6 and 2.9 MB for *pay*, 1.1 to 1.3 s each on the probe's database. Now a key reads fifty a column (180 KB) and the whole list follows once the keys have paused 600 ms, so the rows under the box fill in a moment after typing stops.

**A page shown again reads only what changed** (Björn, after the fourth pass's numbers: "The first and third. Also check if we can apply the first rule to other sources aswell"). Every role view (Tickets, Code, Builds, Monitors; Docs already read only on runs) read its whole view on every return, whether or not anything had synced. Now it reads on its return only if a run of its role's sources ended with something new, or its *Sync now* ended, while it was hidden. Code reads its checkouts on each return regardless, since git on disk changes without a sync. On the live scale estate a return to Code went from 79 reads, 860 KB and a dimmed list for 440 ms to 65 checkout reads (17 KB, last at 48 ms) and no dimming; Tickets, Builds and Monitors read nothing. The repository page keeps its read of the branch list on return: it reads the source, for branches no sync has brought yet (the third pass's rule). Code's pull request groups window from 100 rows, so the tab's 140 ms frame as it opens is gone; their columns are a `colgroup`'s now, because a windowed group's first row is a spacer.

**Four more, measured on a clone of the saved scale database** (Björn, after the fifth pass: "all four"). Each answer is the one it was; the before and after are in the PR's comment.

- **A typed word's board read.** Three statements each read every ticket's wide `sync.item` row (113 MB of heap at 20,000 tickets) and fetched its stored status and assignee row by row. Migration `0074` adds an index-only path for both (the tickets' kind, source, id, title and times; the stored status and assignee), the statements walk a payload only through its primary key where nothing stored answers, a kept card's payload is decompressed once, and the sources' statuses are read beside the cards instead of after them. The search's first word tests the stored assignees as a set built once, wherever the stored declarations say a row is stored (`knobas_core::stored_under!`), where it probed each ticket for its row. **Ruling:** for that first word the stored declarations decide where a stored assignee answers, and the triggers of `0063` keep a row there; a row deleted from under them reads as none, where the probe walked. Every other reader still probes.
- **Code's checkouts.** A return asked each of 65 repositories for its checkout, and each call walked the whole clones root and ran `git status`. Now one call (`entity_checkouts`) for every repository on the page, cloned or not, so a clone made in a terminal still shows: the root is walked once, and git runs only where a stamp of what it reads moved (ADR-0021 as amended). An unstaged edit moves the stamp, so it shows too.
- **Tickets' suggestions.** The ticket keys' values decompressed each sampled record once per field; now once. With nothing typed the parents rank the 2,000 newest parent rows, and every row when those do not fill the list.
- **Standup's digest.** The blockers by status walked every live item's assignee and status; they read only the kinds that declare a blocked set, by their stored values, and *yesterday*'s day reads use an author index.

**Reversing it** is `MORE_STEP` in `tf/tickets/tickets.ts` set past any column's size, and the list line dropped.

**Each ticket's card, stored** (Björn, 2026-11-11, after the sixth pass's numbers: "Just do it if it means the app becomes more snappy"). A typed word's board read was still 141 to 215 ms in the window: the cards walked each kept ticket's fields out of its payload, the search tested the stored assignees and the parents' names in two scans of their own tables, and the sources' statuses probed 23,000 tickets' stored status one at a time. Migration `0075` keeps a row per ticket in `sync.item_card` with every field a card draws (status, assignee and its name, priority, type, epic line, labels and the first of them, comment count, the parent it names, the names it answers to as a parent, and its parents' names lowered for the search), written by the item triggers in the transaction that writes the ticket. The board, a saved view's statuses, the sources' statuses and the search's words read it; the same answers, pinned by `knobas-app`'s `tests/it/item_card.rs` with every card, some and none.

- **Ruling: a stored card is read only under the declarations it was written under.** Its key is the MD5 of every part of the source's declaration the fields read (`sync.card_key`); a reader binds its own declarations and takes a row only where the keys are equal, and walks the payload where not. One row a ticket, for the adapter its source is configured with: a source given another adapter keeps rows nobody reads until its tickets are next written.
- **Ruling: a change to the declarations that reaches tickets drops every card**, and bring-up fills them again in the background, 500 tickets a batch, after it stores the declarations. 0075 computes nothing at the migration: the fill is 1.8 s of the database's time on 23,000 tickets, so the app opens at once and a ticket's reads walk its payload until its card is written. A batch writes only tickets with no card, so a sync beside it keeps its own.
- **Ruling: a typed word tests a ticket's parents' names on its card**, the names `sync.item_parent` holds for it, lowered and joined by U+001F. A word holding that character is held to the names one by one, so it never matches across two. The card is written after `sync.item_parent` in the same trigger, and dropped with it on a declaration change.
