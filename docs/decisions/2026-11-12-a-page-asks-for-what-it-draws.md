# 2026-11-12: A page asks for what it draws, and a press never waits behind a sync

**Asked (Björn, on PR #2479):** the app should feel instant everywhere. The query audit of that day (on the saved scale database: 20,007 tickets, 5,032 pages, 1,710 pull requests, 2,620 builds, 218 monitors) found reads that asked for far more than the page drew, one request per row where one would do, and one press that waited for minutes. This record covers its items 2, 4, 7, 8 and two parts of 12; the other agent's record covers the rest.

**Found and taken.** Times are a release build of the windowless backend (`examples/headless_ipc.rs`) on an APFS clone of the saved database, the head before (`7133eab8`) against this change, on the same clone, each read warm, median of five.

- **Code read every pull request before it could count them.** Four 500-row reads in series, 725 ms and 539 KB, and each later page was dearer than the last (89, 146, 204, 230 ms) because the path line and the state chip were computed for every row the page skipped. Now:
  - The four plain list statements cut the page first and compute the path and state for its rows alone (`entity_list.rs`, `plain_page!`): the same four pages are 73 ms each, the whole list 264 ms.
  - Code reads the newest 100 first (20 ms, 31 KB) and the rest once they are wanted: the list's end scrolled into view, the filter bar set, or a job's count on the tab. Rows a later read brings are older than every row drawn, so they join the end of *Merged or closed* and nothing drawn moves (`2026-11-11-rows-stay-where-they-drew.md`). The open pull requests still come whole from the attention read, which decides the order, so the order is right on the first draw.
  - Unfiltered, the filter bar's count says every pull request, *1,710 pull requests*, not *244 of 1,710*: the list holds them all, read as the reader scrolls to them. Filtered, it counts what the filter keeps, once the rest is read.
  - `code_facts` is asked once for each row as its read lands, not for all 1,775 ids twice: 251 ids, 12 ms and 34 KB on the first screen, against 76 ms and 251 KB.
  - A repository page asks for its own pull requests by the repository's name (`EntityFilter.parent`, read from the stored parents, `sync.item_parent`) and keeps those whose path line is that name, as it did: 8 ms and 15 KB for `scale-data/warehouse-loader`, against 252 ms and 538 KB for every pull request of its source.
  - What it leaves: the attention read is still 196 ms, because it resolves the state of every pull request before it orders them. Code's first draw waits for it on purpose; the answer cache holds it for every open after the first. The cure is a stored row (state, tone, path) for every kind, a migration this pass does not add.
- **Tickets: every j or k sent seven requests at once.** A moved selection now draws at once with what is held of that ticket's preview (the reader keeps the last 40) and reads after it has stood still for 120 ms, the launcher's preview pause. The first selection and one back from none read at once. The four sections and the reach are one command (`card_reads`), which walks the reach once: a settled selection is three requests (the description, `card_reads`, the sub-task board) in 28 ms against seven in 54 ms, and holding j over ten rows sends three, not seventy.
- **A ticket opened through a chain, and many pages asked `get_entity` once a row.** `entity_briefs(ids)` answers each id's kind, source, title and state chip, read as `get_entity` reads its row, in the order asked. A job address asks it for its candidates and reads only the ticket among them whole (six details, five of them misses, become one brief read and one detail: 3.8 ms against 5.5); where the briefs name no ticket every candidate is read as before, so a miss or a failure says what it said. Week's twenty rows are one read of 2.6 KB in 1.7 ms against twenty of 143 KB in 14 ms; Standup's linked tickets, the write queue's names and Docs' reach steps are one read each. The ticket's reach, sections and Code no longer wait for `promote_context`: the reach seeds from the context's adds, and a context promotion makes has none.
- **Refresh waited behind a running sync for the whole run.** A run holds its source's lock for the whole run, network included (74 to 242 s in the saved log), and *Refreshing…* stayed up all that while. The reader's *Refresh* now takes the lock only if no run holds it, and otherwise answers at once: *Jira is syncing now. This page updates when that sync ends.* (`EntityRefresh::RunInFlight`). A landed write's read-back still waits for the lock, in the background, so what the write made is read after the run that may have begun before it.
- **The badges re-read six times a wave.** `badges.refresh` is coalesced: while a read is out, any number of run ends and activity lines make one more read after it.
- **`entity_checkouts` was 262 statements for 65 repositories.** Every repository and override is now one statement (`checkout::REPOS_OF`): 1.6 ms against 11.1.

**Same answers.** Each changed read is pinned to the read it replaces: the cut page against the old statement over every order, with and without the withdrawn, on rows that tie on dates and titles; the parent filter against the path line; `card_reads` against the five reads; `entity_briefs` against `get_entity`; `views` against `view`; the coalesced badges; the briefs path of a job address against the plain one.

**Reversing it.** Code: `FIRST_PRS` as large as the room (`TfCode.svelte`) reads every pull request first again. The preview: `previewPause` 0. Refresh: `Lock::Wait` in `sources::refresh::of_reader`. The others are each one call site going back to the read beside it.
