- **Migration `0042` and the IPC command schema — issue #976 (2026-10-17): the routes no monitor watches, on *Assets nothing watches*.** Spec #808, milestone TF4, requirement R-11.3. Amends #449's entry (`449-no-migration-twenty-first-assets-command.md`) for `UnmonitoredAsset`. No new command, no event, no `WriteOp`, nothing under `crates/knobas-source/src/**`, no new module in either barrel or in `commands/`.

  **The migration.** `alter table knobas.route add column monitors text[] not null default '{}'` with `route_monitors_chk` (no null, no blank), `0020`'s column and check on the route table. A route had no place for the name of a monitor that does not exist yet, and *Create monitor* records the name first so the poll attaches it. `knobas_sync::attach::UNATTACHED` reads the names of both tables, so the poll draws `monitored-by` from `route:<uuid>` to the monitor as it does from an asset.

  **`RouteEdit` gains a variant**, `Monitors { added: Vec<String> }` (`{ field: "monitors", added: string[] }`), `AssetEdit::Monitors`' append on the route's column: a name the route already carries changes nothing and writes no line; the line says `added`.

  **`UnmonitoredAsset` gains `url`** (`Option<String>`, `null` on an asset) and the answer gains rows: a route no confirmed `monitored-by` link to a monitor reaches is a row of `type_id: "route"`, `type_label: "Route"`, `monogram: "RT"`, whose `id` is `route:<uuid>`, `path` is where the exposing asset sits with its own name last, and whose `environment` and `owner` are the exposing asset's, in force. The routes follow the assets, ordered by the exposing asset's path, then its name, then the route's name. The launcher's `not-monitored` list stays assets only.

  **`RouteDetail` gains `monitor_targets`** (`Vec<MonitorTarget>`), filled by the `get_route` command as `get_asset` fills the asset's, so the dialog on a route offers the same sources.
