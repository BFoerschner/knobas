# The shell draws a role, never a source

ADR-0022 gave Builds and Docs shell-owned frames that an adapter fills by declaration, but only for those two, and only by implication. Tickets stayed Jira-shaped: JQL, `jira_views.rs`, and lanes named after Jira's fields. Adding GitHub, a second ticket system or another wiki meant finding out case by case which screens would light up. Björn, 2026-10-18, wanted *"an interface that has like necessary requirements the source has to meet"*.

Decided 2026-10-18 (Björn, custom-sources grilling): **every surface the shell draws beyond one entity's detail belongs to a [role](../../CONTEXT.md#role), and the shell draws it for every source that fills that role, never for a named source.**

- **The built-in roles and their minimums.** Each role requires its read side: kinds, [declared paths](../../CONTEXT.md#declared-path) and live reads. Each write is optional and declared on its own. The shell draws an undeclared write disabled or absent, under ADR-0020's rule. **The normative list of every role's kinds, declared paths, reads, optional reads and writes is `role::MINIMUMS` in `crates/knobas-source/src/role.rs`**; the bullets below describe each role's shape and name no write vocabulary of their own. (*Amended 2026-10-22, review planning, finding SPI-8:* the bullets used to restate the writes, and had drifted from the code on every role: the code host's list had gained `approve`, `merge_pull_request`, `edit_pull_request` and `update_pull_request_branch` and spelled `merge` as `merge_pull_request`; the ticket system's `edit` and `worklog` were never ops and the code has `log_work`; monitoring's "create and edit" is `create_monitor`, `pause_monitor` and `resume_monitor`. An adapter author reading the ADR declared `merge` or `worklog` and the battery refused the descriptor. A list that is a frozen surface lives in one place, and the §10.8 entry that changes it is the ADR's amendment.)
  - **Code host.** Requires `repo`, `branch`, `pr` and `commit`; parent, PR state chip, head and base, the commit a record stands at, requested reviewers, merged flag and default branch; clone URLs; PR, commit and file diffs, the repository tree and file contents, and line threads. Its optional writes are the code host's `writes` in `role::MINIMUMS`.
  - **Ticket system.** Requires `ticket` with key, status, priority, assignee, type, labels, parent and project, and `reachable_transitions`, which a source that does not declare `transition` answers with a refusal by name (#1225: a read-only ticket system has no moves to offer). Its optional writes are the ticket system's `writes` in `role::MINIMUMS`. **Saved views** the source offers are optional too, such as Jira's boards and filters or GitHub Projects. Each is synced as an item and becomes a ticket view; its kind declares where the view's query is, and may declare its board type, sub-query and sprint (#2050). A source's own query language stays the source's: `translate_query` is an optional read, and JQL is Jira's answer to it.
  - **CI.** ADR-0022's Builds frame: `pipeline` and `run`, and `run_log`, required. The other live reads and the build writes are optional, as `role::MINIMUMS` lists them.
  - **Wiki.** ADR-0022's Docs frame: spaces, a page with its parent, and `DocContent`. The page writes are optional, as `role::MINIMUMS` lists them.
  - **Monitoring.** `monitor` with a state and a response time, from which knobas takes its samples. Its monitor writes are optional, as `role::MINIMUMS` lists them.
- **A source can fill several roles,** and it fills a role only where the checks of ADR-0028 pass.
- **A source whose items fit no built-in role declares a custom role,** namespaced to the adapter that declares it (`grafana:dashboard-host`). No other adapter fills it. Its view is drawn from ADR-0020's blocks, never from UI the adapter ships, and it opens when one of the role's items is opened. A custom role has no surface to open by itself yet. A custom role that two adapters need becomes a built-in role in a knobas release.
- **A write outside every role's vocabulary is a [source action](../../CONTEXT.md#source-action),** one `WriteOp` variant (`source_action { id, fields }`). The adapter declares its dialog, as ADR-0020's actions do. The write queue holds and refuses it like any write, and the shell never reads it. The ops of a role stay typed, because the shell acts on them itself: *Start work* creates a branch.

Amended 2026-10-19 (Björn, architecture review): **the mirror answers a role; the shell asks for one and filters nothing.** Which sources fill a role is decided once, server-side, from the registry's claims and the recorded role checks of ADR-0028, and every read a role's surface is drawn from takes that answer: a read that is one role's by definition (the pipelines, the Docs tree, the Monitors roster) narrows to its fillers with no argument, and a read several surfaces share (the entity list, the ticket board) takes the role as a parameter, which narrows its sources and, where no kinds are named, its kinds to the role's. The shell no longer keeps a list of claims to drop rows against after a read.

- **Why.** Until then the claims rode on the source list and each page kept its rows to the fillers after reading them: twelve sites on six pages, and two client registries picking a role's kinds two ways. Every role change (#1196, #1200, #1230, #1256, #1278) edited the same sites, and a page that forgot one drew a source for a role it did not fill. Tickets alone narrowed its read, because its counts are the server's; that is now the rule for every surface.
- **What changes for a row whose source fills nothing.** Items a removed source left behind, and items of a source whose adapter is no longer installed, were drawn on role surfaces because the shell could not name their source's claims. They are not fillers, so no role surface draws them; they stay live for search, the launcher and the detail.
- **What stays with the shell.** Whether a source answers an optional read of a role (`translate_query`), and whether a source claims CI for a staleness warning when it has no rows, are not row filters and stay read from the source list (`app/src/lib/tf/roles.svelte.ts`, #1300). The kind registry's run frame stays only to route a run's address, which row opens Builds' run page; what a section or a count holds is the mirror's answer for the role. `app/src/lib/shell/house-rules.test.ts` fails when a page under the ticket-first shell filters rows by source.
- **Considered and rejected:** deciding fillers in SQL from the role-check table alone. A source that has never synced has no row, and an adapter uninstalled without its sources being deleted leaves rows behind; the registry stays the one source of claims.

## Considered options

- **Keep ADR-0022's frames implicit and add per-source code where needed.** Rejected. That is how Tickets became Jira's, and every new system would ask again which screens it gets.
- **Let an adapter ship its own UI for a custom role, in a sandboxed iframe.** Rejected for ADR-0020's reasons. It would also be a second sandbox beside the WASM one, and it would not follow the app's look or theme.
- **Only the role vocabulary for writes.** Rejected. Every external adapter would be limited to the writes of the knobas release it was built against.

## Consequences

- Generalises ADR-0022: its Builds and Docs frames stand as the CI and wiki roles, and the roles now also cover Code, Tickets and Monitors, so a new CI or wiki source needs no case-by-case wiring.
- `jira_views.rs` and the Jira source line on Tickets become the ticket system's saved views. Gitea's issues reach the Tickets screen once the Gitea adapter syncs them as tickets, which it does not today.
- Each role's minimum is a frozen surface. Changing it is a §10.8 entry.
- The contract suite grows a per-role check, which the built-in adapters pass before the WASM host exists.
