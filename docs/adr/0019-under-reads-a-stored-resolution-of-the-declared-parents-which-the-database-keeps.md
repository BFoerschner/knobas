# `under:` reads a stored resolution of the declared parents, which the database keeps

`under:<name>` (ADR-0018) needs to know which items answer to a name as their parent's, or as a parent themselves. The declarations that say where a parent sits are compiled into the binary, so every query bound them as one jsonb parameter and walked every live item through them. At 100,000 items, with Gitea commits carrying their repository, that walk cost 335 ms to report unknown tokens and about as much again to scope the statement. The launcher's budget is 100 ms (spec §14), and no index can serve a walk whose paths are a query parameter. Decided 2026-10-12 (the deputy's ruling on #627, **proposed until Björn signs off on #627**): **the walk's answer is stored, and the database keeps it.** Migration `0028` adds `sync.parent_declaration`, each adapter template's `payload_paths`, and `sync.item_parent`, one row per `(name, kind)` an item answers to, indexed on `lower(name)`. Database code fills `sync.item_parent` by running the existing `declared_parent_names!` and `declared_names_as_parent!` expansions. It runs when an item is written, when a declaration changes, and when a source's adapter kind changes. Readers ask the index. The app writes `sync.parent_declaration` from the same template list it builds its searcher with, in one function, `Searcher::declaring`.

This is the schema's **first trigger**, and its **first stored value that depends on something outside its own row**: an item's parents depend on its payload, on its source's configured adapter kind, and on that adapter's declarations.

## Considered options

- **Keep the per-row walk and tune it.** Building the declarations once per statement, fencing the walk with `materialized` and `offset 0`, and avoiding set-returning calls per row brought the whole call from about 650 ms to about 180 ms. The coverage probe's 28 ms and the statement's full-mirror scan left no route under 100 ms. The fences also hold only as long as the planner keeps choosing the same plan.
- **Cache the known names in the searcher.** A newly synced parent would read as unknown until the cache refreshed, which breaks "unknown-token reporting answers exactly as before". It also leaves the scoped statement's walk in place.
- **A generated column.** A generation expression may read only its own row and may not contain subqueries or set-returning functions. The macros are made of both, and the declarations live outside the row.
- **The sync writer fills a `text[]` column through the Rust resolvers.** Rejected for three cases. A declaration that changes in an upgrade would wait for a cursor bump and a full re-sync of every source. A row written by anything other than the writer, which includes every search test's seed and a restore, would be empty. And the Rust side would decide the filter while the SQL macros drew the path line, so only a test would hold the two together. A lowercased array would also lose the name's case and the parent's kind, which `under:` suggestions show (#615).

## Consequences

- **One SQL implementation decides both the filter and the path line.** The trigger runs the same macros the path line runs per result row, so the stored rows are what the walk returned. `resolve_parents` keeps its role from #594 as the Rust twin, held to `declared_parents!` by `crates/knobas-core/tests/it/payload_paths.rs`. A migration is SQL and cannot call a Rust macro, so `0028` carries the expansion as text. `knobas-search`'s `tests/it/item_parent.rs` fails if either macro's expansion changes until a new migration restates the function.
- **No Rust on the write path.** `knobas-sync`'s writer is unchanged, no adapter's `CURSOR_VERSION` moves, and no source re-syncs to fill the table. An upgrade that changes a declaration recomputes every affected item when the app first writes the new declarations.
- **Writes to the mirror pay for the resolution.** `sync.item`'s insert and update triggers are statement-level, over the transition tables, so a batch resolves in one pass rather than one function call per row. They resolve only the rows of sources that declare something. Measured on `seed_corpus(100_000)`: 5.15 s without the trigger and 5.31 s with it.
- **One lock orders the two kinds of change.** A write to `sync.item` takes `pg_advisory_xact_lock_shared(627, 0)`, and a change to what the declarations say takes it exclusively. Without the lock, an item inserted while a declaration change was still uncommitted would resolve against the old declarations, and the change's recompute would never see the item. Concurrent syncs share the lock and never wait on each other. A statement that changes no declaration returns before taking the lock, so a search command never waits on a sync.
- **The stored rows are derived and never in a backup.** The `sync` schema is outside every archive (§16.12). A restore lands before any mirror row can exist, and the re-sync's inserts resolve themselves.
- **A bare searcher answers `under:` from the database.** `Searcher::new` with no templates used to answer `under:` with nothing. The answer is now whatever the database has stored. The app always builds its searcher through `Searcher::declaring`, so its behaviour does not change.
