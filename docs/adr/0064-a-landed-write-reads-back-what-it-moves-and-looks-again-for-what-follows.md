# A landed write reads back what it moves, and looks again for what the source does after it

Widens [ADR-0031](0031-refresh-is-an-optional-read-of-one-item-serialized-behind-the-run.md), with [ADR-0047](0047-a-refresh-under-a-parent-walks-it-as-a-run-and-moves-its-position.md)'s walks as the scoped read. Spec #2586, audit #2587. Björn, 2026-11-27: "whenever I do any action anywhere, I want to see the changes appear rather immediately, not just when they're synced at the next full sync." The rule below is the orchestrator's ruling from his words; he may redirect it. Accepted with #2592, which builds rule 1 (2026-11-27).

## Today

After a write lands, `after_landing` (`crates/knobas-app/src/sources/write_queue.rs:895`), the one place every send path reaches, does three things in order:

1. **Refresh one item** (`write_queue.rs:897`): the item the write made, when the op's receipt names one (`WriteOp::receipt_names_an_entity`, `crates/knobas-source/src/lib.rs:2078`), otherwise the write's target (`read_back`, `write_queue.rs:977`). The engine asks `Source::refresh` and, on `NotOffered`, `Source::refresh_under`, the walk of that item's [parent](../../CONTEXT.md#parent) (`crates/knobas-sync/src/refresh.rs:232`).
2. **Follow a run in flight** (`write_queue.rs:927`): where that item is a build the write started, it is read again until it finishes (`crates/knobas-app/src/sources/follow_run.rs:188`, ADR-0031's 2026-11-25 amendment).
3. **Run the write's source** (`write_queue.rs:928`, `Scheduler::sync_after_write`, `crates/knobas-sync/src/scheduler.rs:2160`): an incremental run of the whole source, waited for. Everything else the write moved *in that source* arrives through this run. It is slow where the source is large (a Gitea run takes minutes at Björn's size), a later write's read-back stands it aside (ADR-0031's 2026-11-24 amendment), a source that syncs only by hand gets no run at all (`scheduler.rs:2161`, ADR-0056), and **no other source is run**.

So the gaps are: effects that only the whole-source run reads; effects in another source, which nothing reads until that source's next scheduled run; and what a source does on its own seconds after the write, which nothing reads until the next run.

## Decision

1. **A write kind declares its effects, and after it lands knobas reads back the written item and each effect at once**, each at its own source and in its own place: a refresh by id or the walk of one parent (ADR-0047), never a run of a whole source. An effect is named in knobas' terms, not one adapter's, and resolved from the mirror: *the target's parent* (a pull request's repository, from its declared parent), *the items the target links to* (a pull request's tickets, in whatever source holds them), *the views that hold the target* (a Jira board). The effects are part of the op's delivery, stated beside `WriteOp::delivery` (`lib.rs:1790`) with no wildcard arm, as ADR-0006's 2026-10-19 amendment asks for anything the queue does per op. The run of the write's source still follows, as ADR-0031 says.
2. **What the source does later is looked for on a short, bounded schedule**: about 5 s, 15 s, 30 s, 60 s and 120 s after the landing. Each item stops once it has moved since the read-back. One schedule per scope at a time, and a new write in the scope restarts it. Reads use `Lock::Try` and the background lane after the first, as the follow of a run does; a refresh that finds the item unchanged costs the window nothing (ADR-0031's 2026-11-25 amendment). #2585 is the first case: code and builds after a branch change.
3. **An effect knobas cannot read back is said, not waited on in silence.** The write's toast or the page names it: "Shows after the next sync of *source*". That covers a kind its adapter does not refresh, a source that syncs only by hand, a source turned off, and a read that failed.
4. **Nothing waits on the read-back to draw.** The [echo](../../CONTEXT.md#echo) stays as today. The read-back replaces it in place, with no layout shift (`just moves`).

## The audit

What each `WriteOp` the queue sends moves, and what reads it back today. Every adapter that declares the op is listed with its write arm; an op no row lists for an adapter is refused by it (battery clause 5).

How it is read today:
- **R**: a refresh of the item by id (`Source::refresh`).
- **W**: the walk of the item's parent (`Source::refresh_under`, ADR-0047).
- **F**: followed until it finishes (`follow_run.rs:188`).
- **run**: only by the incremental run of the write's own source that follows the write (step 3 above).
- **live**: drawn from the source's live view (`Source::view`), read again whenever the page reads.
- **none**: nothing until the other source's next scheduled run.

## Gap groups

- **Effects**, #2592 (Rust): the declared effects and their read at once, rule 1. The rows marked *effects*, and the linked tickets of a merged pull request. Every later group builds on it.
- **#2585** (Rust and front): code and builds after a branch change, rule 2's first case. The rows marked *#2585*. Its triggers are the writes whose effects name a repository, so it is blocked by #2592.
- **Jira views**, #2593 (Rust): Jira reads a board or filter view by id, and a ticket write names the views that hold or may now hold the ticket as effects. Blocked by #2592.
- **Build chain**, #2594 (Rust): a build a write started brings its snapshot-dependency chain, each build read by id and followed until it finishes.
- **Schedule**, #2595 (Rust and front): rule 2 beyond branches. The written item and its linked items are read again on the bounded schedule, for bots, automation and automatic merges. Blocked by #2585 (the schedule) and #2592 (the links).
- **Say so**, #2596 (Rust and front): rule 3 for every row marked *say so*, and for any effect whose read answered `NotOffered` or failed. Blocked by #2592.

## What the rule cannot cover

- A change outside every source knobas reads: a deploy, a message in a chat, a system knobas has no adapter for.
- What a source does after the schedule's last read (a nightly automation, an approval hours later). The next run brings it. A build the write started is the exception: it is followed until it finishes.
- A push made outside knobas, or by a command run in the checkout (ADR-0060): knobas did not make the write, so it has no effects to read. A git sync that finds the branch head moved is #2585's second trigger.
- A source's change that no read by id or by parent can see: Gitea's recomputed mergeability of other pull requests, which leaves `updated` alone. Their pages read it live.
- An external adapter's parent effects, until the WIT world carries `refresh_under`. That growth is its own decision (ADR-0028). Until then rule 3 says so.

## Rejected

- **Run every source an effect lives in.** A run of a whole source is what the spec is moving away from: minutes at Björn's size, and it waits behind or stands aside for other writes.
- **Poll until something changes.** It is unbounded, and a write whose source never reacts would keep reading forever. The schedule ends at 120 s.
- **Effects per adapter.** It would make the SPI adapter-aware (ADR-0006). An effect is named in knobas' terms and resolved from the mirror's declared parents and links, so an external adapter's merge gets the same effects as Gitea's.
- **Write the expected effects into the mirror** (mark the base branch moved, the issues closed). The receipt carries an id and nothing else (ADR-0031), and a guess drawn as fact is worse than an echo.

## Consequences

- `WriteOp::delivery` grows an effects answer: a §10.8 change to `crates/knobas-source/src/**`, announced in the effects ticket's PR. The WIT does not change: an op crosses as JSON.
- A landed write costs more reads: one refresh or walk per effect at once, and up to five quiet reads per scope on the schedule. An unchanged read writes nothing and tells the window nothing.
- The glossary gains *effect* (`CONTEXT.md`, *Acting on sources*).

## As built (#2592, 2026-11-27)

- **The declaration** is `WriteOp::effects` (`crates/knobas-source/src/lib.rs`), a match with no wildcard arm that `WriteOp::delivery` copies into `Delivery::effects` (`crates/knobas-spi-types/src/delivery.rs`). An effect is a `knobas_spi_types::delivery::Effect`: `Parent` (the target's declared parent) or `LinkedTickets` (the live tickets a confirmed link joins to the target, either end). `MergePullRequest` declares both, `UpdatePullRequestBranch` declares `Parent`, and every other op declares none yet; each later gap group adds its rows there, and a new kind of effect is a variant of `Effect` with its resolution in `effects.rs`.
- **The read** is `crates/knobas-app/src/sources/effects.rs`, called by `after_landing` after the item's refresh and the follow of a run, and before `sync_after_write`. Each declared effect is resolved against the write's target from the mirror; duplicates, and the item already read back, are read once. The reads go at once and side by side, each through `sources::refresh::refresh` on its own source with the same stand-aside as the item's read-back, and each that read tells `item:refreshed` with the write's id. Each waits behind a run of its source at most 10 s (`Lock::WaitAtMost`, Postgres's `lock_timeout` on the lock's ask): a run that may not stand aside (a person's press, a first sync, a backfill) lasts minutes, and the write's own run, and every caller that waits out the write's follow-up, would wait with it. It answers an `EffectRead` per item (`Read`, `Unchanged`, `NotOffered`, `RunInFlight`, `TurnedOff`, `Failed`), which rule 3 (#2596) shows; until then `after_landing` logs what was not read.
- **A parent is matched by the most names.** `sync.item_parent` matches a child to a parent by any one name it declares, and a Gitea pull request names its repository by `full_name` and by `name`, so a repository of the same short name under another owner matches too. Only the parents matching the most of the child's names are read.
- **The run that follows stays**, for every write as before. It still reads what no effect names: the rows of the audit marked *run* for the write's own source, and every op that declares nothing yet. Taking it away for an op whose effects cover all it moves is a later ruling, once the gap groups have landed.

## As built (#2594, 2026-11-27)

- **The build chain is followed, not declared as an effect.** A run kind declares `waits_on`, the runs a run waits on, by key (ADR-0031, amended 2026-11-27). TeamCity writes a build's snapshot-dependency builds beside its record as `waitsOn`, and the follow of a started run (`crates/knobas-app/src/sources/follow_run.rs`) brings each one: it reads it by id at once, then follows it to its end on the started run's clock, within the 5 follows of a source. ## As built (#2585, 2026-11-28): the bounded schedule after a branch moved

- **The schedule** is `crates/knobas-app/src/sources/look_again.rs`. A *scope* (an entity id; a repository here) is read again at 5 s, 15 s, 30 s, 60 s and 120 s after its trigger. Each read is `sources::refresh::refresh` under `Lock::Try` with no write id, in the background lane: a run of the source holding its lock skips that read, and a read that finds nothing new tells the window nothing. One schedule per scope: a new trigger stops it and starts it again from 5 s. At most 8 scopes at once; a ninth stops the oldest. Not taken up again after a restart.
- **Two sides, each stopped once it moved.** The *code side* walks the repository and reads by id the pull request a write was made on (a target whose kind declares `head`); it has moved once a read answered `Refreshed` or `Gone`. The *builds side* walks each of the repository's pipelines (the Builds tab's `repo_pipelines`, #2564's walk), one source's at a time, and has moved once that answer holds a run it did not hold when the schedule began. A side whose reads are all `NotOffered`, turned off or gone ends; a repository no pipeline builds has no builds side. The code side reads first in each step, so a new commit is mirrored before the builds side looks for its run.
- **Triggers.** A landed write whose op declares `Effect::Parent`, read off `WriteOp::effects` in `after_landing`, right after the effects are read and before the run: `CreateBranch`, `CreatePullRequest`, `DeleteBranch` and `CommitFile` now declare `Parent` beside `MergePullRequest` and `UpdatePullRequestBranch`. The scope is the target's declared parent, or the target itself where it is a parent (a branch made on a repository). And a run of a source that ended `ok` and found a `branch`'s declared `commit` changed or new since the source's last run: the tips are noted per source in memory at each run's end, and after each read of knobas' own, so a write's branch is not found moved again by the next run. The first run after the start only takes the note.
- **Said.** Each start, each side that stops and each end is the event `looking:again` (`knobas_sync::scheduler::LookingAgain { scope, code, builds }`), and the command `looking_again` answers the schedules now. The repository's Builds tab says *Looking for new builds…* at the end of its branch's or pipeline's line while the builds side runs.
- **Reuse (#2595).** A side is anything implementing `look_again::Side` (a read, and whether it moved); `look_again::begin(scheduler, scope, sides)` brings the cadence, the restart, the cap, the lock and the event. A scope may be any item.

## As built (#2593, 2026-11-28)

- **A ticket write names the saved views as an effect.** `Transition`, `CreateTicket` and `EditTicket` declare `Effect::SavedViews`: the live saved views (`sync.saved_view`, a ticket system's boards and filters) that hold the item read back (`sync.saved_view_member`), and those that hold any item of its project (`sync.item_project`, under the adapter its source is configured with), which may hold it after the write. It is resolved against the item read back, not the target: a ticket filed names its project as its target, which the mirror does not hold, and the new ticket is read back first, so its project is known. Gitea's ticket writes declare the same effect and resolve to nothing, having no saved views. A view that holds no ticket of the project yet is not found; the next run of its source brings it. At most 8 views are read (`SAVED_VIEWS_AT_MOST`), those holding the item first, then by id: each read opens a connection of its own and waits on its source's lock beside the others, and a project on a large Jira sits on dozens of boards; the rest are brought by the run that follows. The resolution reads no adapter's key or query, and scans `sync.saved_view_member` once, against the project's items hashed from one range of `item_project_census_idx`.
- **Jira reads a view by its key.** `refresh` still answers `NotOffered` for `board-N` and `filter-N`; `refresh_under` reads one: a board's record (`GET rest/agile/1.0/board/{id}`), configuration, filter, active sprint and its one keys-only search, or a favourite filter's record (`GET rest/api/2/filter/{id}`) and its search, through the reads and mappers a run uses, so the item is the one a run emits. A view a run would leave out (gone, unreadable, a query Jira refuses, a filter no longer a favourite, a setting that no longer brings it) walks to its tombstone; a board record refused with 403 is a failed read, as #2374's refused listing is not gone. The view's fingerprint in the cursor is its position and moves with it (ADR-0047 as amended 2026-11-28); nothing else in the cursor moves. The view kind declares `refreshes: true`.
- **The search index.** The view's keys come from Jira's search, which lags a write. `after_landing` reads the ticket back first, and the ticket's refresh waits until the index holds it as written (`crates/knobas-source-jira/src/refresh.rs`, `PATIENCE`), so the views read after it search an index that has the write.
- The audit's *Jira views* gap in the `Transition`, `CreateTicket` and `EditTicket` rows describes the state before this change.

## As built (#2595, 2026-11-28): the written item and its linked items on the schedule

- **Every landed write** starts a schedule (`look_again::after_write`, from `after_landing` after the effects are read): the item it made or touched (the read-back's item) and the live tickets a confirmed link joins to it (`effects::linked_tickets`, what `Effect::LinkedTickets` names), at most 8 (`ITEMS_AT_MOST`), the item's own first. Not scheduled: an item not live, of a source turned off, or of a kind its adapter's template does not read by id (`refreshes`); the *say so* rule (#2596) speaks for those. Nor the read-back's item when the follow of a run reads it to its end (`follow_run`).
- **One side per item** (`ItemSide`, `SideKind::Item`), read by id under `Lock::Try` at 5, 15, 30, 60 and 120 s. **Moved** is the same for every kind: the mirror holds the item otherwise than when the schedule began (just after the write's read-back), over the columns whose change rewrites its row (`ITEM_UPSERT`: kind, title, body text, author, `updated`, payload, link), or no longer holds it live. So a ticket moves with its status, assignee, `updated` or comment count, a page with its version, a pull request with its state, head, checks, mergeability or comments (Gitea's record and body text carry them), a run with its state. A change a run of the source brought between two steps counts too: the side does not read on for a move already mirrored. An item that moved is not read again; one whose read is not offered, or whose source is turned off, ends.
- **One schedule per write.** The scope is the read-back's item; for a write that moves a branch (`Effect::Parent`, #2585) the item sides join the repository's schedule instead, after its code and builds sides, and the repository itself is not an item. Two schedules started by one write would read the same source at the same steps, each under `Lock::Try`, and one would skip every read the other made. The pull request a branch write was made on is now an item side of that schedule, no longer read by the code side, so it stops on its own move. A new write on the same item restarts its schedule; the cap of 8 schedules holds across both kinds.
- **Said.** `LookingAgain` gains `items` (an IPC change, §10.8): whether an item side is still read. No page draws it yet; the item's page reads again on the `item:refreshed` an item side's read that moved tells (no write behind it), as for any refresh.

## As built (#2596, 2026-11-28): what was not read is said

- **The telling.** After the effects are read and before the run that follows, `after_landing` tells the shell once per landed write what it did not read back, on the event `write:unread` (`knobas_sync::scheduler::WriteUnread`, its lines `Unread`): the item read back where its own read was not offered or failed, each effect whose read answered `NotOffered`, `RunInFlight`, `TurnedOff` or `Failed`, the saved views past the cap of 8 (`EffectAnswer::LeftOut`, the first one left out, said by its source), and what else the write moved where nothing names it: everything on a source that syncs by hand (`UnreadWhy::ByHand`, no run follows), or a source's own action on a scheduled one (`UnreadWhy::Unknown`). A write read back whole tells nothing. The choice is `effects::unsaid`, a pure function; `effects::tell` names each line with the item's title, the source's name, whether it syncs by hand, and when it runs next, only for a scheduled source other than the write's (the write's own runs right after it).
- **The toast, not the page.** The shell says it in one toast (`app/src/lib/shell/unread-toast.ts`), one sentence per source and wording, naming one item and counting the rest: *PAY-231 shows once the sync of Jira under way ends.*, *Retry SEPA payouts shows after the next sync of Jira, in about 14 min.*, *The other boards and filters with PAY-231 show after the next sync of Jira.*, *What else the write to Fix rounding moved shows after Sync now on Gitea.*, with *Sync now* on the toast for a source that syncs by hand. It stays 10 s and goes earlier once what it names arrives: a refresh of the item, or the end of a run of its source that began after the toast (any run's end, for one under way). The page holding the echo was not used: a write lands from a dozen surfaces, the item's page may not be open, and a line on a page would move what is drawn under it.
- **Pleasant's direct write** (outside the queue) says it in its own toast: `WriteAnswer::Written` carries `path_unread`, true when the entry went to the mirror in a folder with no path (moved or made there; the one listing it was read back from names no ancestors), and the toast reads *Saved the entry. Its path shows after the next sync of Team passwords.* (*after Sync now on …* for a source that syncs by hand).
- **Uptime Kuma with only an API key** needs nothing: such a source cannot write (`crates/knobas-source-kuma/src/refresh.rs`, the module note), so no landed write reads a created monitor as gone.
- **An external adapter** without `refresh` (WIT before 1.4.0) tells its item as not offered, and every external adapter's parent effects stay *said* until the WIT carries `refresh_under`.
