# Desktop notification click channel (issue #339)

Research note, 2026-09-04. Question owned by issue #339; the code this is about is
`app/src/lib/inbox/notify.svelte.ts` (header comment, "The click, and the one thing
this cannot witness") and the §10.8 entry for #290 in `docs/contract.md`.

## Question

knobas pins `tauri-plugin-notification = "=2.4.0"` (`crates/knobas-app/Cargo.toml:72`)
and `@tauri-apps/plugin-notification` `2.4.0` (`app/package.json:15`) on Tauri core
2.11.5 and `@tauri-apps/api` 2.11.1. The frontend subscribes to `onAction` so a
clicked notification navigates to the inbox item whose address rides in `extra`;
on desktop that subscription rejects, because `onAction` invokes
`register_listener`, which the plugin only registers on mobile. Has the plugin,
since 2.4.0, gained a way for a desktop app (macOS first) to learn that a
notification was clicked? If not, what are the alternatives and what does each
cost?

## Answer

No. 2.4.0 is the newest release of both packages (crates.io and npm, both published
2026-08-31), and the plugin's source at `plugins-workspace` HEAD
(`a21555dd`, 2026-09-03) has no change to `plugins/notification/` since the
`notification-v2.4.0` tag. On desktop the plugin still registers three commands
and hands the notification to `notify-rust` fire-and-forget. What *has* changed
is one layer down: `notify-rust` 4.18.0 (2026-06-16), which this repo's
`Cargo.lock` already resolves, exposes a click on macOS, Linux and Windows through
`NotificationHandle::wait_for_action` — the plugin simply drops that handle. The
upstream request for click events (#2150) has been open since 2022-03-14 with no
maintainer commitment; the only working desktop implementation cited there is a
third-party crate (`user-notify`) that bypasses the plugin.

## Findings

### What 2.4.0 does on desktop

- The plugin's invoke handler lists exactly `commands::notify`,
  `commands::request_permission`, `commands::is_permission_granted`.
  `plugins/notification/src/lib.rs:228-232` at tag `notification-v2.4.0`
  (identical at HEAD `a21555dd`).
- The desktop `show` builds a `notify_rust::Notification`, on macOS calls
  `notify_rust::set_application(if tauri::is_dev() { "com.apple.Terminal" } else
  { &self.identifier })`, then `tauri::async_runtime::spawn(async move { let _ =
  notification.show(); })` and returns `Ok(())`. The handle `show()` returns is
  discarded, so no click can be observed. `plugins/notification/src/desktop.rs:179-221`.
- `onAction(cb)` is `addPluginListener('notification', 'actionPerformed', cb)`.
  `plugins/notification/guest-js/index.ts:570-574`. `addPluginListener` invokes
  `plugin:notification|register_listener` (then falls back to the camelCase name)
  — `@tauri-apps/api` 2.11.1, `node_modules/@tauri-apps/api/core.js:154-166`. The
  only `register_listener` implementations are Android
  (`android/src/main/java/NotificationPlugin.kt:130`, `trigger("actionPerformed", …)`)
  and iOS (`ios/Sources/NotificationHandler.swift:70`). A permission file
  `permissions/autogenerated/commands/register_listener.toml` exists, so a
  capability grant would not fail the build; the command just is not there on
  desktop. Confirms the header comment in `notify.svelte.ts:59-71`.
- The plugin depends on `notify-rust = "4.11"` for macOS/Windows/Linux/BSD
  (`plugins/notification/Cargo.toml`, `[target.'cfg(any(target_os = "macos", …))'.dependencies]`).
  knobas's `Cargo.lock` resolves `notify-rust 4.18.0` and
  `mac-notification-sys 0.6.15` (`Cargo.lock:3323-3324`, `3151-3152`).

### What the latest version does

- Latest versions: `tauri-plugin-notification` 2.4.0 on crates.io, published
  2026-08-31 (previous 2.3.3, 2025-10-27); `@tauri-apps/plugin-notification`
  2.4.0 on npm, published 2026-08-31T11:20Z; no newer tag.
  Source: `curl https://crates.io/api/v1/crates/tauri-plugin-notification/versions`,
  `npm view @tauri-apps/plugin-notification time`, `git tag -l 'notification-v*'`.
- `git diff --stat notification-v2.4.0 HEAD -- plugins/notification` is empty at
  HEAD `a21555ddd2eaadfed23848912fe2802c2ba7579e` (2026-09-03). So "latest" and
  "pinned" are the same code.
- The 2.4.0 CHANGELOG entries are Gradle `consumer-rules.pro` (#3531) and "Add
  Rust builders for **mobile** notification action types" plus an Android
  action-group fix (#2805). Nothing desktop.
  `plugins/notification/CHANGELOG.md`, `## [2.4.0]`.

### What notify-rust can do per OS (4.18.0)

- CHANGELOG `v4.18.0 (2026-06-16)`: "add common wait_for_response on all
  platforms", "add wait_for_actions and on_close using mac-notification-sys",
  "macos: add mac-usernotifications backend", "add Windows notification handles".
  https://github.com/hoodie/notify-rust/blob/v4.18.0/CHANGELOG.md
- Support table in the crate docs: `NotificationHandle::wait_for_action` is
  ✔︎ for XDG, macOS (`NSUserNotificationCenter`), macOS (`UNUserNotificationCenter`)
  and Windows; `Notification::action(...)` is ✔︎ XDG, "⚠︎ (labels only)" on the NS
  backend, ✔︎ UN, blank on Windows. `src/lib.rs:82-108` at v4.18.0.
- macOS default backend is `NSUserNotificationCenter`; `UNUserNotificationCenter`
  is opt-in via the `preview-macos-un` cargo feature. `src/macos/mod.rs:1-38`.
- NS backend, `src/macos/nsusernotifications.rs`:
  - line 7: "This stack is deprecated on macOS 14+, but still works." (Apple's
    own page dates the deprecation to macOS 11.0 — see Apple sources below.)
  - lines 29-31: `wait_for_action` "**Requires the main run loop to be running.**
    … if nothing is pumping the main run loop this call will block indefinitely."
    A Tauri app pumps it; the plugin's spawned task runs on a worker thread and
    would block that thread, not the UI. Whether that combination actually works
    inside Tauri is **not verified** here.
  - lines 42-61: `wait_for_action` calls `send_mac_notification(…, asynchronous:
    false, …)` and maps `NotificationResponse::Click` → `"default"`,
    `ActionButton(label)` → label, `CloseButton | None` → `"__closed"`.
  - lines 142-162: `impl Drop for NotificationHandle` sends the notification
    `asynchronous: true` if the handle was not consumed — which is what the
    plugin's `let _ = notification.show()` triggers. So the plugin's path is "show
    on drop, never wait".
- `mac-notification-sys` 0.6.15 (`~/.cargo/registry/src/*/mac-notification-sys-0.6.15`):
  - `objc/notify.m:17-25` `setApplication` only accepts a bundle identifier that
    Launch Services can resolve (`LSCopyApplicationURLsForBundleIdentifier`) and
    then fakes the process's bundle identifier to it. This is why the plugin
    passes `com.apple.Terminal` in dev and the app identifier in a bundle.
  - `objc/notify.m:74-77`: "shouldWait: if NO, returns immediately after delivery
    … if YES, blocks until the user interacts or the notification is
    auto-dismissed." `objc/notify.m:252-284`: the
    `didActivateNotification:` delegate maps
    `NSUserNotificationActivationTypeContentsClicked` to activation type 2 (Click).
  - The delegate is process-global (`setupDelegate`, `src/lib.rs:49`, called via
    `ensure_delegate_initiated()` at `src/lib.rs:82`).
- Linux (XDG): `wait_for_action` maps `NotificationResponse::Default` →
  `"default"` (`src/xdg/mod.rs:101-128`). The freedesktop spec: "The default
  action (usually invoked by clicking the notification) should have a key named
  `"default"`." https://specifications.freedesktop.org/notification/latest/protocol.html.
  So on Linux the app must add `.action("default", "…")` for a body click to be
  reported at all; the plugin adds no actions.
- Windows: handles with `wait_for_action` / `on_close` exist
  (`src/windows.rs:111`, `:136`); no `action()` support in the table. Not
  examined further — knobas targets macOS first.

### Apple's own statements (for the activation fallback)

- `NSUserNotificationCenterDelegate.userNotificationCenter(_:didActivate:)`:
  "Sent to the delegate when a user clicks on a user notification presented by
  the user notification center." Platform: macOS 10.8, deprecated 11.0;
  "All NSUserNotifications API should be replaced with UserNotifications.frameworks
  API". Also: "To take an action when your application is launched as a result
  of a user clicking on a notification, be sure to implement the [applicationDidFinishLaunching]
  method … if that dictionary has the `NSApplicationLaunchUserNotificationKey`
  key …". https://developer.apple.com/documentation/foundation/nsusernotificationcenterdelegate/usernotificationcenter(_:didactivate:)
  (read via `/tutorials/data/documentation/….json`).
- `UNUserNotificationCenterDelegate.userNotificationCenter(_:didReceive:withCompletionHandler:)`
  (macOS 10.14+): "The response can also indicate that the user dismissed the
  notification interface, or launched your app, without selecting a custom
  action." https://developer.apple.com/documentation/usernotifications/unusernotificationcenterdelegate/usernotificationcenter(_:didreceive:withcompletionhandler:)
- `NSUserNotificationCenter`: "it may suppress the notification if the application
  is already frontmost (the delegate can override this action)." — consistent with
  the "unfocus the window" step in `testenv/README.md:808`.

### Third-party crate: `user-notify`

- https://github.com/Simon-Laux/user-notify, crates.io 0.4.2 (2026-01-23), repo
  HEAD `f27eeb25` (2026-05-18). README: "Uses system APIs directly", "Buttons in
  notifications (macOS, todo: windows, Linux)", "Notification can persist across
  sessions and can be used to start your app (windows, macOS)"; history section:
  written "because [tauri's notification APIs] did not implement all notification
  features … (Basic features like reacting to clicks on notifications were
  missing in the rust api)". System requirements: "on macOS this only works inside
  an app package with a 'Bundle ID', also you need an Apple developer account to
  sign it" and "you can use the 'mock' implementation in debug mode which just
  logs to the console." Action buttons on Linux/Windows are open issues (#1, #2).
  Whether a plain body click (no button) is reported on Linux/Windows is not
  stated in the README and was **not verified**.

### Fallback mechanisms and what each would require from knobas

Ground truth on this side: the plugin is registered at
`crates/knobas-app/src/lib.rs:151`; the app's identifier is `dev.knobas.desktop`
(`crates/knobas-app/tauri.conf.json:5`); Rust→JS events are constants in
`crates/knobas-app/src/lib.rs:56-65` and §10.8 treats the event schema as frozen
("No … IPC command, event, module-layout or barrel line", `docs/contract.md:518`;
the #290 entry states "Nothing new crosses the bridge as an event"). The signed
dev-bundle recipe is `testenv/README.md:747-808`.

1. **Wait on the notify-rust handle in the app's own Rust code (bypass the
   plugin's `notify`).** Build the `notify_rust::Notification` in knobas, call
   `show()`, then `wait_for_action` on a worker thread; on `"default"`, either
   emit an event with the address or call the router. Needs: a new Rust→JS
   **event** (§10.8 entry) or a new **command** the frontend polls (§10.8 entry);
   a bundle identifier Launch Services can resolve (dev: the
   `com.apple.Terminal` trick, or the signed dev bundle); on Linux, adding
   `.action("default", …)` to the notification; a live check that a blocked
   worker thread inside Tauri receives the delegate callback (unverified). Uses the
   NS backend Apple deprecated in 11.0 unless `preview-macos-un` is enabled — that
   feature is marked preview in `src/macos/mod.rs:20-21`. Depends on nothing
   upstream; the frontend's `onAction` path would be replaced, not fed.
2. **Upstream the same thing into the plugin** (add a desktop `register_listener`
   that keeps the handle and triggers `actionPerformed`). This is what would feed
   the existing `onAction` subscription unchanged and cost knobas nothing but a
   version bump. Depends on a plugin release; #2150 shows four years without one.
3. **`user-notify` crate directly.** Replaces the plugin on desktop. Needs a signed
   bundle for anything to happen on macOS (mock in debug), the same new
   event/command as option 1, and a second notification stack to maintain.
   Depends on a one-maintainer crate at 0.4.x.
4. **Deep link.** `tauri-plugin-deep-link` 2.4.10 configures desktop schemes in
   `tauri.conf.json > plugins > deep-link > desktop.schemes`; runtime
   `register`/`is_registered` are "macOS / Android / iOS: Unsupported"
   (`plugins/deep-link/src/lib.rs:254-259`, `:425-431`), so the scheme only works
   from a built bundle. **It is not a click channel on its own**: nothing in
   notify-rust's API opens a URL when a notification is clicked (support table,
   `src/lib.rs:82-108`), and Apple's delegate is the only thing that learns of the
   click. A deep link would need option 1 or 3 to open it, at which point it is
   redundant.
5. **Window activation plus newest inbox item.** macOS activates (or launches) the
   app when its notification is clicked (Apple, didActivate page). Tauri exposes
   `WindowEvent::Focused(bool)` (`tauri-2.11.5/src/app.rs:127`) and, for the
   dock/reopen path, `RunEvent::Reopen` (`src/app.rs:279`, "Emitted when the
   NSApplicationDelegate's applicationShouldHandleReopen gets called"). The
   frontend can observe focus with no Rust change (`window.onFocusChanged` in
   `@tauri-apps/api`), so **no new command or event** is required. What it
   delivers is "the app came to the front and the inbox shows the newest
   announced item", not "this click, this item"; it cannot tell a notification
   click from an alt-tab, and the app activation on click was reported by a user
   in #2150, not verified here on a knobas bundle.
6. **Keep notifications one-way** (drop the criterion). No cost; the `onAction`
   subscription and the address in `extra` stay as the disclosed, tested door.

## Options for #339

| Option | Delivers | Costs | Depends on upstream |
|---|---|---|---|
| Wait on notify-rust handle in knobas Rust | click → navigate to the item (macOS via NS backend; Linux with a `default` action) | new event or command (§10.8 entry); bundle id / signed bundle on macOS; live check that a worker-thread wait works inside Tauri; deprecated NS API unless `preview-macos-un` | none (notify-rust 4.18.0 already in `Cargo.lock`) |
| Upstream desktop `register_listener` to the plugin | click → navigate, through the existing `onAction` subscription | writing and landing a plugin PR; a version bump here | plugin maintainers; #2150 open since 2022 |
| `user-notify` crate | click → navigate on macOS; buttons; persistence across launches | second notification stack; signed bundle required on macOS; new event or command (§10.8) | third-party crate 0.4.2, single maintainer |
| Deep link | nothing by itself — no OS opens a URL on notification click here | scheme config, bundle-only on macOS | `tauri-plugin-deep-link` 2.4.10; still needs a click source |
| Window activation + newest item | window focus and the inbox's newest announced item; not the clicked item | frontend-only (`onFocusChanged`); heuristic, indistinguishable from other focus | none |
| Keep one-way, drop the criterion | nothing new | none | none |
