# knobas — roadmap: MVP, milestones, parallel workstreams

**Status:** proposed 2026-08-24 (Claude), adopted, and amended per milestone since (M2.5 added 2026-08-30, M2.6 2026-08-31, M3 cut into M3.0–M3.3 and put on the real systems 2026-09-03). Everything here follows from the revised design doc (`docs/specs/2026-08-23-knobas-design.md`) and the 2026-08 technology research (summarized in §Stack below). M0 through M2.5 have shipped, M2.6 is at its exit sweep as of 2026-09-01, M3.0 opened 2026-09-03 (spec #272), and the GitHub milestones carry the live state.

This is the decomposition document: the project is too large for one plan, so it is cut into milestones. Since 2026-08-28, task-level planning runs the mattpocock-skills flow (grilling → spec → tickets in GitHub Issues); the executed superpowers-era plan files (M0/M1) remain in git history — see §6.

## 1. What "MVP" means here

Björn's stated pain: **bad source-system search (JQL/Confluence) and credential juggling.** The earliest build that beats the status quo at that is the MVP:

> **MVP = end of M1: sources connected once (credentials in the keychain), everything synced locally, one `⌘K` box that finds any ticket/PR/build/page in <100 ms, context rooms and detail views to read it all in one window.**

That build is read-only toward the sources, has no links UI, no timer, no assets — and is already worth opening every morning. (Since no real Jira/Confluence/TeamCity instance is available during development, every milestone is developed and accepted against the local test environment — §3 — and "start using it daily" begins at the deferred real-system gate, the day real credentials exist.) Everything after M1 makes knobas *knobas* rather than a fast index:

- **M2** is the identity release (links, suggestions, write-back, start-work, inbox).
- **M2.5** delivers the mini board (the Tickets tile's status-grouped rendering, plus a status select in the ticket detail).
- **M2.6** adds project rooms and gives the mini board a second layout, so the room a person stands in decides both what its tiles hold and how its mini board is drawn.
- **M3** makes it the whole workday, in four gated sub-milestones and against the real systems (ADR-0013): **M3.0 Witness** (the real Jira and Confluence seeded, the Jira adapter certified), **M3.1 Time** (timer, blocks, worklogs, timesheet), **M3.2 Confluence** (the adapter, read and write), **M3.3 Daily flow** (digest, standup protocol, desktop notifications).
- **M4** adds the estate (assets, monitoring, share export) in three gated sub-milestones (M4.0 Estate, M4.1 Monitoring, M4.2 Share export; cut 2026-09-06). Flowrun left the plan that day: the real system is Orchestra, a later feature.

Ship order M3 vs. M4 can be swapped by pain; nothing in M4 depends on M3.

## 2. Milestones

### M0 — Foundation (one stream, sequential; plan 01, written)

The contract-freezing milestone. No parallelism yet — everything later builds on these interfaces, so one agent (or the session itself) does it carefully.

Contents: Cargo workspace + Tauri 2 + Svelte 5/Vite scaffold · embedded Postgres lifecycle (`postgresql_embedded`, PG 18.6 pinned, TCP localhost) · migration baseline (schemas `knobas` + `sync`, FTS with `GENERATED ALWAYS AS (...) STORED`) · `knobas-core` (EntityRef, links, activity) · `knobas-source` SPI (the `Source` trait + contract-test battery) · the Tidewater seed dataset as machine-readable fixtures + `--demo` loader · `knobas-source-mock` · minimal sync run (mock → `sync.item` → FTS) · IPC commands (`search`, `sync_now`, …) with typed TS bindings · `just check` gate.

**Exit criteria:** `just check` green; the Tauri window opens; `--demo` loads Tidewater; searching "sepa retry" over IPC returns PAY-231 grouped results from Postgres FTS.

**Freeze on exit:** (1) the `Source` trait, (2) the migration baseline, (3) the IPC command/event schema. Later changes to any of the three go through the orchestrator and a doc update, never unilaterally inside a workstream.

### M2 — Links & actions (the identity release; 4–5 streams)

Links UI everywhere (panels, *Link to…*, Tab action chains, `[[refs]]`) over the one link table · suggestion engine (keys in commits/branches/build params/page text, FTS similarity, native source links; reasons; dismissals persisted) + room tray · write-back: Jira status/comment/create, Gitea branch/PR/comment/approve, TeamCity trigger/re-run · write queue with conflict UI (re-read before flush, ask with diff) · **start-work flow** + reverse (PR merged → In Review) · inbox v1 (mentions, review requests, failed builds, assignments, credential expiry; actions; snooze with date) · notes (markdown, `[[…]]` chips, backlinks) · contexts complete (promote ticket, ad-hoc, 1-hop membership, per-context inbox filter) · scheduled **backup export** (`pg_dump` of `knobas`).

**Exit criteria:** ticket→branch→PR round-trip against the test environment (real-container Gitea; mockd Jira transitions); inbox populated and actionable end-to-end; links/suggestions working over the synced corpus; a nightly backup archive exists.

### M2.5 — The mini board (serial, one stream; added 2026-08-30)

The Tickets tile becomes the **mini board** the design doc promised (§2 Shell: "Tickets (mini board)"): status columns over the context's live ticket items, each column headed by its status name and count, cards showing key, priority, and title, clicking through to the ticket detail — plus a status select in the detail slide-over, enqueued as a transition through the existing write queue (optimistic; the source refuses illegal moves by name and the refusal surfaces in the pending/held-write UI). One additive IPC read command is the milestone's only frozen-surface touch (§10.8 entry). Vocabulary per ADR-0009: *mini board*, "board" never unqualified.

**Gate:** opens only at M2 exit (Björn's gate); closes before M3 starts. Nothing in it is `ready-for-agent` before then.

**Exit criteria (against the test environment):** the tile renders the mini board from the granted read, with the empty state; a status move round-trips through the write queue and an illegal move surfaces in the conflict UI; the paperwork is merged (design-doc addendum, this roadmap insertion, ADR-0009, the §10.8 entry). Spec: issue #175.

### M2.6 — Project rooms and the mini board's two layouts (two streams, merged serially; added 2026-08-31)

M2.5 leaves a multi-project Jira with one room for all of it, drawing a mini board that is the union of every workflow's statuses in a tile too narrow to hold it — the problem ADR-0010 states, and the one this milestone answers twice over. A **project** (`CONTEXT.md`, **Project**; ADR-0010) becomes a scoping dimension a room can be built on: the switcher grows a room for every project a source's corpus shows, listed under that source's own room, and standing in one narrows every tile in the room rather than the Tickets tile alone. And the **mini board** gains a second layout, chosen by the room: a bounded room (a project room, a stored context) keeps M2.5's column layout, a definitionally unbounded room (*All work*, a source room) draws the same status groups stacked one under another and scrolling down, and a demote-only backstop at six columns keeps a bounded room that turns out to span two workflows off a horizontal scrollbar. Two frozen-surface touches — a project dimension on the room filter, and an additive read reporting the projects a corpus shows — carry a §10.8 entry each, written with the changes that make them. Vocabulary per ADR-0009 and ADR-0010: *mini board*, "board" never unqualified; *project* per the glossary, never a synonym for *context*.

**Gate:** opens only at M2.5 exit (Björn's gate); closes before M3 starts. Nothing in it is `ready-for-agent` before then.

**Exit criteria (against the test environment, except where the demo profile is named):** under every source room whose corpus shows projects — mockd Jira and mockd TeamCity both do — the switcher lists a room per project, labelled by the project's own name, and by its key where the project reports no readable name; standing in one narrows every tile in the room, and — where the source has tickets, which mockd Jira does and mockd TeamCity does not, the mini board being the Tickets tile and nothing else (ADR-0009; ruled 2026-09-01, #242) — its mini board draws that project's workflow alone in columns, demoting to the stacked layout where that workflow turns out to draw more than six; *All work* and a source room show the same statuses, in the same order, with the same counts and cards, stacked vertically, and the terminal "No status" group is last in both layouts; a ticket whose mirrored record carries no readable project is still reachable in *All work* and in its source's room, appears in no project room, and there is no "No project" room; a bookmarked address for a project the corpus no longer shows lands in *All work*; `just demo` shows project rooms over the Tidewater dataset with nothing configured; the paperwork is merged (design-doc addendum, this roadmap insertion, the two §10.8 entries). Spec: issue #188.

### M3 — Time & the daily flow, against the real systems (four gated sub-milestones; cut 2026-09-03, spec #272)

M2.6 leaves a cockpit that reads everything and writes some of it back, but the workday itself still lives outside it: time goes into a Jira worklog dialog from memory, the standup is assembled by scrolling four systems and typed into Confluence by hand, Confluence pages are not in the mirror at all, and the inbox exists only while the window is in front of you. Each sub-milestone is its own GitHub milestone with its own gate (Björn), and each exit runs every live suite. ~~the 401 credential-health path with the real `X-Seraph-LoginReason` header~~ — amended 2026-09-03 by witness (ADR-0013: the real container decides, and this is what it decided), #296; the clause in the criteria above replaces it. The criterion as first written asks the product for a header it does not send. Measured on Jira 10.3.24 by #276, a bearer token the instance cannot resolve never reaches Seraph: `401` with no `X-Seraph-LoginReason` on `/serverInfo`, `/myself` and `/issue/{key}/…`, and `200` with `total: 0` on `/search`, which needs no permission to ask. The header comes from a wrong *password* only, and a few wrong passwords lock the account (`403 Basic Authentication Failure - Reason : AUTHENTICATION_DENIED`), so no suite may take its 401s that way against an account it also needs. What the engine acts on was never the header: the adapter classifies 401 and 403 alike as `Unauthorized` (interfaces §4.1), so the amended criterion asks for the status. `knobas-source-jira/tests/live_jira_seeded.rs`'s `a_rejected_credential_is_a_real_401_and_only_basic_auth_carries_the_seraph_header` pins both schemes, and `knobas-mockd` deviation 14 records the divergence. Björn keeps the milestone gate; if the amendment is overturned, the criterion as first written cannot be met by any test that does not lock the admin account out.

### M4 — Assets, monitoring, estate (4–5 streams)

M3 leaves a cockpit that reads and writes the work and tracks the day, but the machines the work runs on are not in it: no asset has an address, no monitor reaches the inbox, and what knobas owns can be backed up but not shared. M4 adds the **estate** (`CONTEXT.md`, **Estate**: the whole tree of assets, their routes and the monitors attached to them) in three gated sub-milestones, cut the way M3 was and grilled 2026-09-06 (Björn + Claude, `/grill-with-docs`). Two rulings reshape the August plan. **The estate is the real test infrastructure, not the Tidewater fiction**: the three Hetzner servers, the local Gitea and Uptime Kuma, the notebook, the tunnel's forwards as routes — described in `testenv/estate.json` with stable ids, loaded by an *Import* in the Assets view and by `--demo` — because ADR-0013's lesson applies to assets too: data about a real estate is a witness, a made-up estate is a mock. And **Flowrun is gone**: the real system is called **Orchestra**, it is a later feature and not a milestone, and the asset types *runtime* and *scenario* stay generic so the tree can hold an Orchestra instance by hand until an adapter exists; ADR-0013's single exception is void with it, and port 8213 is unreserved. Vocabulary per the `CONTEXT.md` **Estate** section (estate, asset, route, monitor, alert, import) and its **Tree** entry (the Assets view's first tab — never "board", ADR-0009); containment is a parent field, not a link (ADR-0014). Every frozen-surface touch below carries a §10.8 entry, written with the change that makes it. Each sub-milestone is its own GitHub milestone with its own gate (Björn). Spec: the M4 spec issue, written by Björn after the grilling.

#### M4.0 — Estate (opens now)

The asset model: infinite tree by parent field, the built-in type table from spec §12.1 with monograms and typed-property schemas (*runtime* and *scenario* replacing the Flowrun-branded types), custom properties (text / number / date / url — the *secret* type and its keychain convention are deferred), routes, every other relation as a link, environment and owner inherited from the nearest ancestor that sets them, history from the activity stream. The Miller-column **Tree** with spines, wires, the fixed right pane and search-reveals-the-path; create at any level; **Import** of an estate file with a preview of what is already in the tree; assets in the launcher with their path, in the room's Assets tile (a stored room: member assets through ancestors; *All work*: the estate's top level with problem counts; a source room: the assets its monitors attach to; a project room: nothing), as timer targets and as the foreground entity of an observation, and in contexts through ancestors (ADR-0008's latent clause lands here). Deferred out of M4.0: the *secret* property type, the "Depends on this" panel, asset smart lists and save-search-as-list, the status-page dialog. Frozen-surface touches: the asset and route migrations, the asset IPC module, `Kind` gaining `asset` and `route`.

**Exit criteria:** the real estate imported from `testenv/estate.json` and browsable in the Tree; an asset found in the launcher with its path, timed, and reached in a context through an ancestor; a re-import previews "already in the tree" for all of it; `just demo` shows the same estate beside the Tidewater work.

#### M4.1 — Monitoring (opens at M4.0 exit, in parallel with M4.2)

The **Uptime Kuma adapter** as an ordinary source: one source, the API key required at add-source for `/metrics`, the account optional and added later in the same keychain envelope, write ops advertised only when the account is present. A poll is an ordinary sync run — every run full, `monitor` an exhaustive kind so a deleted monitor is swept, interval per source with a one-minute default, upserted counting the monitors whose state or reading changed. One sample per poll per monitor into a knobas-owned timeseries with a retention setting (default 90 days; in the backup, out of the share export), which draws the Monitors tab's 24 h bar. One global response-time threshold (default 1500 ms) makes the *warn* state. An **alert** is a monitor's crossing into down or warn, one open per monitor, knobas-owned state keyed on the monitor entity with no address of its own; the inbox's sixth category `alert`, subject the monitor entity, reaching the inbox only when some context holds the affected asset (directly or through an ancestor); opening it lands in the Tree at that asset; **ack** is knobas-local and clears the inbox item while the alert stays open; recovery closes the alert and removes an un-acked inbox item with a history line; the desktop-notification category `alert`, off by default. A monitor attaches to an asset by a `monitored-by` link, drawn by the estate import (the file names each asset's monitors by their Kuma name), by *Link to…*, and by a droppable suggestion ticket (the monitor's URL host matches an asset's hostname or route). The **Monitors** tab: state chips with counts, the 24 h bar, last checks, uptime and cert days, open-alert cards, the "Not monitored" roster (a query over assets), pause/resume only when the account is present. The Kuma room exists like every source room; Kuma declares no projects. The real Kuma's monitors: a ping per Hetzner server (the firewall opens only 22 and ICMP), HTTP on the three products through the tunnel — labelled as such, since they fall with it — HTTP on local Gitea, and a **canary** on a throwaway port the live recipe binds and releases; the two mockd monitors leave the seed, and no live run ever stops a shared container. Last and droppable at the gate without failing the milestone: *Create monitor for this asset* and pause/resume over socket.io (`kuma-client`). Frozen-surface touches: the Kuma adapter's descriptor and `monitor` kind, the timeseries and alert migrations, the sixth inbox category and its notification category, the two-secret keychain envelope, the write ops if they land.

**Exit criteria (against the real Kuma container):** the Kuma live suite green; the canary knocked down by the recipe opens an alert that reaches the inbox because a context holds its asset, ack clears the inbox item and the alert stays open until the canary recovers, and recovery closes it; the timeseries holds the run's samples; create and pause monitor if they landed.

#### M4.2 — Share export (opens at M4.0 exit, in parallel with M4.1)

The curated **share export** (`CONTEXT.md`, **Share export**; spec §16.12 as amended by #283) as the same `pg_dump` custom-format archive the backup uses, restricted to the tables the toggles select, so the existing restore path reads it unchanged and `pg_restore` can open it by hand. Parts, as tables: links (with the entity rows they reference), assets (asset and route), contexts, notes, time (timer, block, worklog, heartbeat, time settings), sources (source configurations, which hold no secrets). Defaults: links, assets, contexts and sources on; notes and time off. Smart lists are built-ins only today, so that toggle does not exist until a saved list does; the activity stream is never in a share export. **Merge-restore with preview is not in M4**: restore stays empty-database-only, and a merge is v1.5 the day there is a second machine or a colleague to merge for.

**Exit criteria:** a share export with the default toggles restores on a clean machine, contains no note, no block, no worklog and no secret, and the links in it resolve once the same sources are configured; a toggle turned on brings its part and nothing else.

## 4. Stack (decided by research 2026-08-24; pins live in plan 01)

| Layer | Choice | Why (short) |
|---|---|---|
| DB | **PostgreSQL 18.6 via `postgresql_embedded` 0.21**, download-on-first-run, TCP 127.0.0.1; "existing PG URL" setting | 0.12 s start, 21 MB idle, ships `pg_dump`/`pg_restore` (export = free), proven (Retrom); sidesteps the open Tauri macOS `externalBin` notarization bug |
| DB access | **sqlx 0.9** (`runtime-tokio`, explicit features), embedded `migrate!` at startup | compile-checked raw SQL is right for FTS; diesel only wins on typed tsvector, not enough |
| App shell | **Tauri 2.11**, `tauri::async_runtime::spawn` for the scheduler, events for state changes, `ipc::Channel` for sync progress | events are explicitly not for high throughput |
| Secrets | **`keyring` crate 4.x directly** | `tauri-plugin-stronghold` is deprecated; `tauri-plugin-store` is unencrypted |
| HTTP | **reqwest 0.13** (+ middleware/retry + `governor` rate limiting) | rustls default now reads the macOS keychain roots — corporate certs work; skip `tauri-plugin-http` (pins reqwest 0.12) |
| Frontend | **Svelte 5 + Vite** (no SvelteKit), mockup CSS kept global, Bits UI for primitives, TanStack Virtual for columns/lists | runes ≈ the mockup's imperative logic; region-by-region port via `mount()` |
| Adapters | hand-rolled reqwest per source; exceptions: `gouqi` (Jira, handles Cloud-v3/DC-v2), Gitea client codegen from `/openapi3.v1.json`, `kuma-client` (Kuma config) | a sync app needs 5–15 endpoints, not 400 generated ones |

**Gotchas every implementer must know** (verified in research, encoded as constraints in the plans):

1. PG 18: `GENERATED ALWAYS AS (...)` without `STORED` silently creates an unindexable virtual column — always write `STORED`.
2. sqlx 0.9: dynamic SQL needs `AssertSqlSafe`; keep it in one reviewed query-builder module. Never bind `tsquery` — bind text into `websearch_to_tsquery('english', $1)`, compute the tsquery once as a FROM item. Never map `tsvector` to `String`.
3. macOS Unix-socket path limit (103 bytes) breaks PG sockets under `~/Library/Application Support` — TCP localhost only.
4. **The primary Jira/Confluence dialect is Data Center (self-hosted), not Cloud** — Jira DC REST v2 (`/rest/api/2/search`, `startAt` pagination; the Cloud `/search` 410-removal never applied to DC) and Confluence DC REST v1 (`/rest/api/content` + CQL; no v2 API exists on DC). The `flavor: datacenter|cloud` field in the source config selects the dialect; Cloud (`/search/jql`, `nextPageToken`, no `total`) comes later.
5. Confluence Cloud's CQL likewise exists only in its v1 REST API — on both flavors, CQL is the search path.
6. Uptime Kuma v2 prunes raw heartbeats to ~24 h — knobas records its own timeseries from the first poll; metric absence = *unknown*, not down; response time `-1` is a sentinel.
7. `ts_headline` output is not XSS-safe — escape synced HTML before the webview renders it.
8. sqlx migrations need `build.rs` with `cargo:rerun-if-changed=migrations` or the embedded migrator goes stale silently.
9. Tauri: don't `emit` from the `setup` hook (webview not listening yet) — frontend signals ready first. Stop the scheduler and `pg_ctl stop` on `RunEvent::ExitRequested`.
10. Unsigned dev builds re-prompt the keychain on every run — sign locally.

## 5. Risks beyond the gotchas

| Risk | Mitigation |
|---|---|
| PG major upgrades (data dir incompatible) | pin `=18.6.0`; upgrade = sequenced dump → initdb → restore at startup on version change (we own it; export format is already a dump) |
| First-run binary download (GitHub rate limit / offline) | pinned version skips release lookup; `bundled` feature is the fallback if offline first-run ever matters |
| `rust_socketio` unmaintained (Kuma config channel) | socket.io isolated behind the adapter trait; `/metrics` alone still covers state + telemetry |
| ~~Flowrun API unknown (internal system, no instance available during development)~~ — **closed 2026-09-06 (M4 grilling)**: the feature left the plan. The real system is Orchestra, booked as a later feature for the day an instance is reachable; no stub is built for it, ADR-0013's single exception is void, and port 8213 is unreserved | the asset types *runtime* and *scenario* hold an Orchestra instance by hand until then |
| ~~No real Jira/Confluence/TeamCity during development — mocks could drift from reality~~ — **closed 2026-09-03 (ADR-0013)**: they drifted, and the real containers are the witness now; what remains of the mitigation is the vendored specs as reference material | strongest available contract per API, vendored + checksum-pinned in `testenv/specs/` (Jira DC WADL, TeamCity swagger-from-container, Cloud OpenAPI for later); **Confluence DC has no published machine-readable spec** → validated against the real `atlassian/confluence` container (`--profile real-atlassian`); real-system gate re-runs every milestone checklist once real instances exist |
| ~~Björn's exact DC versions unknown~~ — **closed 2026-08-31 (#49)** | Björn ruled "use the latest datacenter versions", then "the ones demoable with timebomb licences" once it emerged the two differ: `real-atlassian` is pinned to Jira Software **10.3.24** and Confluence **9.2.21**, the newest LTS releases a published timebomb key starts (Jira 11.x is reported to reject it). | ~~Fidelity tests for the vendored specs cover the mocks, not the adapters' assumptions about *behavior* (ordering, defaults, permissions)~~ — **closed 2026-09-03 (ADR-0013)** | the `--profile real-atlassian` and `--profile real-teamcity` containers are no longer a milestone-exit backstop but the witness itself: seeded, run per PR through `just <system>-live`, re-run by the merge-manager |
| Full-page-rerender habits from the mockup leaking into the port | Svelte components own local state; the mockup is a *behavior* reference, its rendering strategy is explicitly not carried over |
| Scope creep before MVP | M2+ features need a milestone, not a slot in the current one; the design doc's tiering is the arbiter |
